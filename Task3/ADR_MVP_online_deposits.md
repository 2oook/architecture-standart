### <a name="_b7urdng99y53"></a>**Название задачи:** MVP онлайн-подачи заявок на открытие депозитов и накопительных счетов на сайте и в интернет-банке
### <a name="_hjk0fkfyohdk"></a>**Автор:** PILY, команда цифровой трансформации розничного бизнеса
### <a name="_uanumrh8zrui"></a>**Дата:** 21.11.2026

**Статус:** предложено.

**Контекст.** Сейчас клиент открывает депозит или накопительный счёт только в отделении. Ставки считаются вручную в Excel и передаются по почте. Бэк-офисы депозитов и кредитов согласуют специальные ставки письмами. Интернет-банк — монолит на платформе подрядчика (ASP.NET MVC 4.5) в одном ЦОД. Он работает напрямую с БД АБС. БД АБС перегружена и масштабируется только вертикально.

Цель MVP (горизонт 6 месяцев):
- клиент интернет-банка подаёт заявку на депозит онлайн и подтверждает её СМС-кодом;
- новый клиент оставляет заявку на сайте, а оператор кол-центра ему перезванивает;
- бэк-офис обрабатывает заявки по старому процессу, но в АБС, а не по почте.

Требования собраны в FURPS+ таблице: [Task2/FURPS+.md](../Task2/FURPS+.md).

### <a name="_qmphm5d6rvi3"></a>**Решение**

#### Диаграммы

- Диаграмма контекста: [C4_Context_MVP_deposits.drawio](C4_Context_MVP_deposits.drawio).
- Диаграмма контейнеров: [C4_Container_MVP_deposits.drawio](C4_Container_MVP_deposits.drawio). На ней детализированы интернет-банк и АБС.

Цвет элемента на диаграммах показывает его статус. Зелёный — новый элемент, синий — дорабатывается, серый — без изменений, тёмно-серый — внешняя система. Пунктир — существующая интеграция, которую MVP не меняет.

#### Ключевые решения

1. **Обмен между онлайн-каналами и АБС идёт асинхронно через Kafka.** Интернет-банк и сайт не вызывают АБС в новом процессе. Заявки ждут в Kafka, пока адаптер не передаст их в АБС. Так сбой или перегрузка АБС не останавливают приём заявок (NFR1, NFR3). Kafka выбрана по требованию IT. Она хранит журнал событий, позволяет перечитать события и подключить новых потребителей. Следующим потребителем станет кол-центр (задание 4).
2. **Новый функционал реализуется отдельными микросервисами на .NET 8 вне монолита.** Монолит на .NET Framework 4.5 несовместим с Kafka. Его ядро обновляет подрядчик. Команда интернет-банка знает C#, поэтому выбрана современная .NET. Для MVP выделены 4 сервиса с разной нагрузкой и ответственностью:
   - сервис ставок и продуктов — нагрузка в основном на чтение, отвечает из кеша;
   - сервис заявок на депозит — заявки из интернет-банка и лиды с сайта, статусы, Transactional Outbox;
   - сервис подтверждения (OTP) — СМС-коды вне ядра платформы подрядчика;
   - сервис уведомлений — единая точка отправки СМС. Позже его используют и другие продукты.

   Это первый шаг перехода интернет-банка на микросервисную архитектуру. В MVP он затрагивает только открытие депозитов.
3. **Монолит интернет-банка работает как BFF для раздела «Депозиты».** Команда банка добавляет в монолит экраны по дизайн-системе. Серверная часть монолита вызывает новые сервисы через API Gateway по HTTPS. Аутентификация клиента и выбор счёта списания остаются в монолите. Ядро платформы при этом не меняется (NFR11). Монолит уже умеет выполнять HTTP-вызовы, поэтому Kafka ему не нужна.
4. **API Gateway на YARP (.NET 8)** — единая точка входа для монолита и сайта. Он маршрутизирует запросы, проверяет сертификаты mTLS, ограничивает частоту запросов и балансирует нагрузку между экземплярами и ЦОД (NFR6, NFR8). YARP написан на .NET, поэтому команда интернет-банка может его сопровождать.
5. **Ставки ведутся в АБС, а не в отдельной системе.** Бэк-офисы уже работают в АБС. В АБС есть остатки клиентов для персональных ставок. Ролевая модель АБС разграничивает доступ бэк-офисов депозитов и кредитов (NFR9). АБС рассчитывает и публикует ставки заранее, поэтому каналы получают их без обращений к АБС.
6. **Интеграционный адаптер АБС на Java 17 и Spring Boot.** В команде АБС есть Java-специалисты. У Kafka полноценный клиент для Java. Адаптер решает две задачи:
   - читает таблицу Outbox пачками и публикует события;
   - читает заявки из Kafka и вызывает PL/SQL API с ограничением скорости.

   Адаптер — единственная точка нагрузки на БД АБС от онлайн-каналов, поэтому её легко контролировать (NFR4).
7. **Надёжная доставка: Transactional Outbox, Inbox и идемпотентность.** Сервис заявок и АБС пишут событие в Outbox в одной транзакции с изменением данных. АБС принимает заявку через таблицу Inbox с уникальным ключом. Повторная доставка не создаёт дубликатов (NFR7).
8. **Высокая доступность.**
   - Новые сервисы работают в Kubernetes в двух ЦОД в режиме active-active.
   - Базы MS SQL реплицируются через Always On Availability Groups.
   - Брокеры Kafka размещены в обоих ЦОД, фактор репликации — 3, `min.insync.replicas = 2`.
   - Монолит интернет-банка разворачивается во втором ЦОД за балансировщиком, сессии хранятся в MS SQL.

   Это закрывает текущее ограничение «один ЦОД — одна группа серверов» (NFR1, NFR2).
9. **Быстрый отклик.** Сервис ставок держит каталог и ставки в памяти. Кеш обновляется по событию из Kafka. Персональные предложения хранятся в БД ставок с индексом по клиенту. Тот же подход — справочники в кеше и обновление по событию — позже устранит медленную загрузку справочников при платежах (NFR5).
10. **Сайт** получает ставки и отправляет заявки через тот же API Gateway. Сайт и интернет-банк используют один источник ставок, поэтому ставки в каналах всегда совпадают.
11. **Система кол-центра** получает лиды из Kafka через новый модуль на Spring Boot. Модуль подключается через механизм расширения платформы. Особые условия оформляются через существующую интеграцию обращений с АБС, поэтому её не нужно менять в MVP.

#### Интеграции

| Источник | Получатель | Протокол | Данные |
| :- | :- | :- | :- |
| Клиент банка | Монолит ИБ | HTTPS | Экраны раздела «Депозиты» |
| Монолит ИБ | API Gateway → сервисы ставок и заявок | HTTPS / REST, mTLS | Ставки, персональные ставки, черновик заявки, код подтверждения, статус |
| Сайт (бэкенд PHP) | API Gateway → сервисы ставок и заявок | HTTPS / REST | Каталог и ставки, лид (ФИО, телефон, продукт) |

| Сервис OTP | Kafka | `notification.sms.requested` | СМС с кодом |
| Kafka | Сервис уведомлений → СМС-шлюз | HTTP API шлюза → SMPP | Текст СМС, телефон |
| Kafka | Адаптер АБС → БД АБС | JDBC, PL/SQL API | Заявка на депозит |

| Kafka | Сервис ставок | Kafka consumer | Ставки, персональные предложения |
| Kafka | Сервис заявок | Kafka consumer | Статусы заявок |
| Kafka | Система кол-центра | Kafka consumer (новый модуль) | Лиды с сайта |
| Система кол-центра | АБС | Существующая интеграция | Обращения по особым условиям |
| Монолит ИБ | БД АБС | SQL, без изменений | Платежи, счета, остатки |

#### Статусная модель заявки

`Черновик` → `Подана` (код подтверждён) → `Принята в АБС` → `Ставка подтверждена` → `Депозит открыт`. Из любого статуса после `Подана` заявка может перейти в `Отклонена`. Черновик без подтверждения удаляется через 24 часа.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

| № | Альтернатива | Почему отклонена |
| :-: | :- | :- |
| A1 | Интернет-банк вызывает API или БД АБС напрямую, как сейчас для платежей | БД АБС перегружена и масштабируется только вертикально. Онлайн-заявки поставят под угрозу работу банка. Команда АБС против. Сбой АБС остановит приём заявок. |
| A2 | Реализовать всё внутри монолита интернет-банка, СМС-коды — через ядро | Нужна доработка ядра подрядчиком: это сроки, стоимость и зависимость. Монолит несовместим с Kafka. Он не масштабируется горизонтально. |
| A3 | Переписать весь интернет-банк на микросервисы | Не укладывается в 6 месяцев MVP. Высокий риск для платежей, которые уже работают. Переход выполняется поэтапно, начиная с депозитов. |
| A4 | Очередь RabbitMQ или IBM MQ вместо Kafka | IT рекомендует Kafka на перспективу. Kafka хранит события и позволяет перечитать их, например для подключения кол-центра и аналитики. |
| A5 | Интеграция с АБС через файлы, ETL или репликацию БД (Oracle GoldenGate) | Файлы и ETL дают задержку в часы. Статусы и СМС приходили бы поздно. Репликация дорогая и создаёт сильную связь со схемой БД АБС. |
| A6 | Вести ставки в отдельном новом сервисе вне АБС | Бэк-офисам пришлось бы работать в двух системах. Персональные ставки требуют остатков из АБС. Ролевую модель пришлось бы строить заново. Вариант можно вернуть к рассмотрению в целевой архитектуре. |
| A7 | СМС о статусах отправляет АБС, как сейчас | Каждая СМС нагружает АБС. Появились бы два канала отправки с разными шаблонами. Сервис уведомлений централизует отправку. |
| A8 | Синхронный запрос персональной ставки из АБС при открытии раздела | Каждое открытие раздела нагружало бы АБС. Время отклика составило бы сотни миллисекунд и больше. |

**Недостатки, ограничения, риски**

| № | Недостаток, ограничение или риск | Как снижаем |
| :-: | :- | :- |
| R1 | Kafka и Kubernetes — новые технологии для банка. Опыта эксплуатации нет. | Обучить инфраструктурную команду, привлечь внешних консультантов на запуск, использовать управляемый дистрибутив (например, Strimzi), подготовить инструкции. |
| R2 | Данные согласованы в конечном счёте (eventual consistency). Статус в интернет-банке может отставать от АБС на секунды. | Показывать клиенту время обновления статуса. Отслеживать задержку потребителей Kafka. |
| R3 | Монолит интернет-банка остаётся точкой отказа, пока его не развернули во втором ЦОД. | Развёртывание во втором ЦОД — отдельная задача MVP. До её завершения доступность 99,9 % для раздела «Депозиты» не гарантируется. |
| R4 | Существующая прямая интеграция монолита с БД АБС для платежей остаётся. Нагрузка на АБС не снижается. | Вне MVP. На этапе целевого решения платежи и счета переводятся на события из Kafka. |
| R5 | Адаптер АБС — критичный компонент. Его остановка задерживает заявки и статусы. | Несколько экземпляров адаптера в двух ЦОД, мониторинг задержки (lag), алерты. Заявки не теряются, потому что ждут в Kafka. |
| R6 | Ограничение скорости в адаптере при пиках увеличит время ожидания обработки заявки. | Бэк-офис обрабатывает заявки вручную, поэтому задержка в минуты допустима. Скорость настраивается без изменения кода. |
| R7 | Ручная обработка заявок бэк-офисом ограничивает пропускную способность. Клиент ждёт ставку часами. | Это осознанное ограничение MVP. Через год открытие депозита станет автоматическим. Нужно сообщить клиенту ожидаемый срок обработки. |
| R8 | Персональные ставки рассчитываются раз в день. Предложение может устареть после крупного движения денег. | Окончательную ставку подтверждает бэк-офис. Интернет-банк показывает дату расчёта предложения. |
| R9 | СМС как второй фактор уязвимо к подмене SIM-карты. | Ограничить сумму онлайн-заявки, проверять смену SIM через телеком-оператора, в будущем добавить push-подтверждение. |
| R10 | Доработка системы кол-центра зависит от подрядчика или от загрузки Java-специалистов команды АБС. | Заранее согласовать объём работ с подрядчиком. Модуль небольшой и использует механизм расширения платформы. |
| R11 | Форма на сайте может стать источником спама и ложных лидов. | CAPTCHA, ограничение частоты по IP и телефону в API Gateway, проверка формата телефона. |
| R12 | Растёт число компонентов, которые нужно сопровождать. | Единые шаблоны сервисов, CI/CD, централизованные логи и мониторинг, документация OpenAPI и AsyncAPI. |
